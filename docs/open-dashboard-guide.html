01

像製作網頁一樣，製作資料畫面。

open-dashboard 是開源的 dashboard 工具：用 SQL 定義「看哪些資料」，用 TSX 定義「怎麼呈現」。開發時可以查詢資料庫、調整面板；建置後可以交付靜態站或單檔 HTML。

01 / WIDGET

一個問題，一個面板

例如「本週 PUE 是多少？」的數字卡、「什麼時段最耗電？」的熱圖。圖表、表格、敘事文字都可以是 widget。

02 / DASHBOARD

為日常營運而組合

把相關面板放在一起，切換案場與觀測週期，找出異常。展示站切換的是預先算好的快照，並非即時設備資料。

03 / REPORT

為一次決策而定稿

固定週期、數據與敘事，回答「發生什麼、為什麼、接著做什麼」。這個 repo 用獨立模板建立可列印、可追溯的週報。

為什麼選它？ TSX／SQL 是 agent 能讀寫、Git 能比較差異的文字；原生 widgets 與 CLI 提供共同語言，能先驗證再輸出。沿用既有 renderer，可把時間放在能源指標與客戶需求上。

代價是：資料語意、發布權限與品質流程仍需要自行設計；靜態交付只涵蓋建置時列舉的篩選組合，自由探索要另接服務。

02

open-dashboard 是引擎。
這個 repo 把它接成能源交付流程。

直接使用原生工具，就能寫 SQL、組圖表、建置畫面；這裡加入客戶、案場、資料契約與快照管理，讓每次交付有一致的依據。

Dashboard 與 Report 的差別是用途與生命週期。 Dashboard 讓使用者探索已提供的維度；Report 固定一次決策的依據。個人移動 widget，不會修改已發布的週報。

03

每一步，都留下可檢查的產物。

從資料到交付是一條建置流程。點選步驟，查看實際檔案與它回答的問題。下方路徑以 runs/<run_id>/ 為根目錄。

01 / INPUT

資料包：先確定數字的意思。

依客戶範圍產生五份 Parquet，固定時間、單位與 seed。現階段是擬真合成資料；正式接入必須先對齊資料契約，再建立新的 run。

  • input/*.parquet站點、設備、電表、遙測與事件
  • generation.json生成範圍、合成標記與來源資訊
  • quality.json能量守恆、SOC、時間間隔等品質結果

相同資料，兩種交付。

營運人員打開 dashboard.html，切換站點；管理者讀取 report.html，引用本週結論。manifest.json 記錄輸入與產物 checksum，讓交付可以核對。

資料更新，就建立新版本。

已建置的 run 不接受悄悄更換資料或模板。新的週期、指標或版型建立新的 run；既有報告保留，避免同一個連結的數字日後改變。

04

可以讓 agent 生成。
先決定誰能改到哪一層。

開發者需要能編輯來源碼的工具；客戶需要受控的指標、widgets 與發布流程。兩條路可共用驗證與建置引擎，輸入介面和權限不同。

DEVELOPER WORKFLOW 下一階段設計

讓 agent 產生或修正 TSX／SQL，再交付固定版本。

例如：「替 Helios 新增 PUE 趨勢與冷卻事件說明。」agent 先讀欄位與計算規則，修改模板、查詢或 widget，驗證後產生可預覽的 Dashboard／Report。

讀契約欄位、單位、指標
改來源隔離草稿 TSX / SQL
查錯與修復最多三次驗證
預覽／審查數據、畫面、差異
發布版本新 run + manifest

已有的底座

原生 CLI 可查 schema、執行 query、檢查模板；repo 有敘事 lint、品質檢查及有界修復 callback。現在的 CLI 不會自行呼叫 LLM 修正。

要補上的串接

把 CLI 包成 agent tools，加上隔離工作目錄、job 狀態與修復紀錄。審查通過後才把來源寫回 Git，並以新 run 發布；避免重建時覆蓋草稿。

CUSTOMER WORKFLOW 下一階段設計

Studio 與聊天，編輯同一份草稿規格。

例如：「做一張兩案場的 PUE 週報，加入冷卻異常。」Studio 用表單與拖曳選擇；Chat 把需求轉成同樣的草稿。系統先確認可用指標與設備，不讓模型自行發明定義。

選擇或描述Studio / Chat
共同草稿指標、版面、週期
編譯與驗證受控 TSX / SQL
客戶預覽範圍、數值、版面
權限發布正式新版本

「新 widget」有兩個層次

第一階段組合核准的卡片、圖表與指標即可。若需要全新互動元件，由開發者建立並測試，再加入 widget 目錄供客戶使用。

客戶選的是業務語意

例如 metric_id = pue，以總設施電量除以 IT 電量，不能平均各筆 PUE。租戶由登入身分決定；草稿規格只是建置輸入，最終仍交給 open-dashboard 呈現。

原生「agent 友好」≠ 現成的客戶生成產品。 已核對 0.7.0 CLI 與程式：原生聊天助手的工具是讀取現有面板、切換篩選；它不負責寫 TSX 或發布報表。本 repo 未設定聊天模型，MCP 也需另裝套件。上面兩條自動生成流程尚未實作。

LLM 提案，資料契約定義答案。

模型可以組合圖表、提出敘事；真實數值仍由 SQL 查詢。新指標需通過語意檢查，租戶隔離由服務強制執行。現有 SQL 範圍裁切只適用受信任模板，不能直接當成任意查詢的權限系統。

只用 HTTP server、Vercel 或 Cloudflare 可以嗎？

展示快照只需 HTTP 靜態服務，GitHub Pages 已經足夠。原生編輯、查詢與建置需要 Node runtime、檔案系統及 DuckDB 原生套件；npx 只是啟動指令，不是另一種 runtime。未來可把 UI／API 放在 Vercel 或 Cloudflare，長時間建置交給獨立 Node worker。Cloudflare Workers 無法直接執行這個 Node 原生 DuckDB 建置流程；Vercel 函式也需評估原生相依、暫存檔與執行時間。

加入 Rill，差別在哪裡？

現在 Dashboard 探索的是已建置的站點與週期。Rill 可作為另一個分析入口，讓使用者沿指標維度繼續探索；需要實際 Rill runtime／Cloud、資料更新與權限整合。本 repo 已匯出 Parquet 與七個 interval 指標，尚未啟動 Rill 服務。它不會自動取代週報發布、agent 工作或客戶 Studio。

DuckDB 之後可以換 ClickHouse 嗎？

可以保留同一份業務資料契約，先由 ClickHouse 擷取限定範圍，再凍結成 Parquet 交給 DuckDB 建置；也可後續改為直接 datasource。前者較容易維持可重現快照，後者需逐一處理 SQL 方言、權限、查詢成本與一致性。目前只有 adapter 邊界與設定範例，未連接真實 ClickHouse。

06

先把產製做好，再把它交到客戶手上。

原 handoff M0–M3 以等權重粗估約完成 85%，是範圍判斷，不是測試通過率。真實資料、實際 agent 修復迴圈與原始報告 CSS 還有缺口；客戶 Studio 是新增產品方向，沒有計入這個比例。

  1. 開發者生成

    包裝 tools 與隔離 job；以「新增一張可驗證的 PUE 週報」作為端到端驗收。

  2. 受控 Studio

    建立指標／widget 目錄、草稿 API、預覽與版本發布；先改善編輯體驗。

  3. Chat 共用草稿

    自然語言轉成結構化修訂；缺少資訊先釐清，未通過檢查不發布。

  4. 企業服務

    帳號、公司共用版型、排程、真實資料接入；依需求加 Rill 探索與 ClickHouse。
